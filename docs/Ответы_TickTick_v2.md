# TickTick — ответы к защите (версия 2)

Каждый ответ сверен с кодом репозитория TickTick. Номер в скобках — номер вопроса в исходном списке.

---

## BACKEND

### (1) Почему FastAPI, а не Django REST Framework?

Бэкенду нужно только отдавать JSON для отдельного React-приложения, без HTML-страниц и встроенной админки Django. FastAPI проще для такого API: роутеры, проверка данных через Pydantic и документация Swagger на `/docs` получаются из коробки.

### (2) Как разделены routers и services?

Роутеры (`app/routers/`) принимают HTTP-запрос, проверяют, чья это запись, работают с базой и возвращают ответ или ошибку. В `app/services/` вынесена логика, не зависящая от HTTP: пароли и токены (`tokens.py`), разбор wiki-ссылок (`wiki_links.py`) и сборка DOCX/PDF (`export_service.py`).

### (3) Как настроен CORS и почему нельзя разрешать все origin через звёздочку?

В `main.py` разрешены только адреса из настройки `CORS_ORIGINS` (localhost:5173, :3000), плюс `allow_credentials=True`. Звёздочка вместе с credentials браузер не принимает, а без credentials она разрешила бы любому сайту слать запросы к API от имени пользователя.

### (4) Как Depends управляет сессией БД?

Функция `get_db()` в `db.py` открывает сессию, отдаёт её эндпоинту через `yield` и закрывает в блоке `finally`, даже если случилась ошибка. Эндпоинт просто объявляет параметр `db: DbSession`, и FastAPI сам создаёт и закрывает сессию на каждый запрос.

### (5) Почему где-то `async def`, а где-то `def`?

Почти все эндпоинты обычные `def`, потому что драйвер `psycopg2` синхронный; Uvicorn запускает их в отдельном пуле потоков и не блокирует цикл событий. `async def` только у загрузки вложений (`await file.read()`), но внутри него запрос к БД синхронный и на это время блокирует цикл событий.

### (6) Как проверяется `.env` и что будет без ключа?

Класс `Settings` (pydantic-settings) читает `.env` и приводит значения к нужным типам: например, нечисловое `ACCESS_TOKEN_MINUTES` вызовет ошибку при старте. У всех полей есть значения по умолчанию, поэтому без ключа приложение запустится с дефолтом — для `JWT_SECRET` в продакшене это опасно.

### (7) Зачем и SQLAlchemy-модели, и Pydantic-схемы?

Модели SQLAlchemy описывают таблицы и связи в базе, а схемы Pydantic описывают, какой JSON API принимает и отдаёт. Так в ответ не попадёт лишнее (например, `password_hash`), а входящие данные проверяются до записи в базу.

### (8) Как сделан централизованный перехват ошибок и 422?

Своих обработчиков исключений нет: ошибки валидации отдаёт сам FastAPI (код 422), а остальные ошибки роутеры бросают через `HTTPException` с `detail={"message": ...}`. К одному виду ошибки приводит фронтенд: `client.js` достаёт текст из `detail.message` и показывает его пользователю.

### (9) Какой драйвер PostgreSQL и есть ли асинхронность?

Используется `psycopg2-binary` (`postgresql+psycopg2://`), он синхронный и неблокирующий ввод-вывод не поддерживает. Для async понадобились бы `asyncpg` и асинхронная сессия SQLAlchemy.

### (10) Как избегается N+1 у заметок?

Список заметок возвращает только id, заголовок, теги и дату, связанные таблицы не трогаются, а теги лежат массивом в той же строке. При открытии одной заметки связи подгружаются через `joinedload` одним запросом; задачи вместе с заметками не загружаются вообще.

### (21) Как хешируются пароли?

Через bcrypt (`passlib` `CryptContext`) в `services/tokens.py`. Соль bcrypt генерирует сам для каждого пароля и хранит внутри хеша, поэтому отдельной колонки для соли нет.

### (22) Из чего состоит JWT и сколько он живёт?

Токен состоит из заголовка, payload и подписи HS256. В payload: id пользователя, email, имя, роль, iss, aud, iat, exp; access-токен живёт 15 минут, refresh — 30 дней, причём в БД хранится только его SHA-256 хеш.

### (23) Как отозвать токен или выкинуть заблокированного пользователя?

При logout и при каждом refresh старый refresh-токен помечается `revoked=True` (ротация), а access-токен отозвать нельзя — он действует до истечения 15 минут. Честное ограничение: при «удалении» пользователя админом (`deleted_at`) обычные эндпоинты и `/refresh` это не проверяют, отсекает только `/login`.

### (24) Где проверяется роль admin?

Зависимость `require_admin` в `deps.py` берёт пользователя из БД и сверяет роль, а все роуты `/api/admin/*` подключают её через `AdminUser`. Роль берётся из базы, а не из токена, поэтому подделать её в токене не получится.

### (25) Как защищены от IDOR?

Каждый запрос к заметке, задаче или событию фильтруется по `user_id` из токена: `Note.id == note_id AND Note.user_id == user_id`. Если подставить чужой id, запись просто не найдётся и вернётся 404.

### (26) Как предотвращены SQL-инъекции?

Все фильтры строятся через ORM SQLAlchemy, а полнотекстовый поиск вызывается с параметрами: `search_notes(:q, :uid)`. Ввод пользователя никогда не склеивается со строкой SQL.

### (27) Почему админа назначают через `UPDATE users SET role = 'admin'`?

Первого администратора некому назначить через API: роль меняет только тот, кто уже admin (`PATCH /api/admin/users/{id}/role`). Поэтому первый admin задаётся вручную в БД, а дальше остальных можно назначать через админ-панель.

### (28) Защита от подбора паролей и спама регистрациями?

Нет: ограничения числа запросов и капчи нет. Есть только одинаковое сообщение «Неверный email или пароль», которое не выдаёт, существует ли такой email.

### (29) Чем опасен `.env` в Git?

Утечёт `JWT_SECRET`, и любой сможет выпускать себе валидные токены, в том числе с ролью admin; утекут и данные подключения к БД. В проекте `.env` занесён в `.gitignore`, в репозитории лежит только `Backend/.env.example`; если секрет всё же попал в историю, его нужно сменить.

### (30) Защита от DoS (огромная заметка, экспорт)?

Ограничений на размер текста и вложений нет, а файл вложения читается целиком в память. Экспорт делается по одной заметке, поэтому нагрузка умеренная; в продакшене нужны лимиты размера тела запроса и rate limit.

### (31) Как парсятся wiki-ссылки в формате двойных скобок?

Регулярным выражением r"\[\[(.+?)\]\]" в wiki_links.py: ленивый поиск до первых закрывающих скобок, пробелы обрезаются, дубли убираются. Вложенные скобки отдельно не разбираются, а ссылка на несуществующий заголовок просто не создаёт связь.

### (32) Как работают обратные ссылки (backlinks)?

Связи хранятся в таблице `note_links` (откуда → куда). При открытии заметки API отдаёт `incomingLinks` — заметки, которые ссылаются на текущую — и `outgoingLinks`.

### (33) Что будет со ссылками при переименовании или удалении заметки?

Текст других заметок не меняется, так что старый синтаксис ссылки в тексте останется как есть; связь пересчитается только когда ту заметку пересохранят. При окончательном удалении строки в `note_links` удаляются каскадом.

### (34) Парсятся ли чекбоксы Markdown и синхронизируются ли с задачами?

Нет: заметка — обычный текст, а задачи живут в отдельной таблице `todos`. При экспорте строки с `- ` превращаются в маркированный список, не более.

### (35) Как считаются просроченные задачи?

Динамически при каждом запросе `GET /api/todos/overdue`: не выполнена, не удалена и `due_at < now()` в UTC. Фоновых задач по расписанию нет.

### (36) Как сделаны повторяющиеся задачи?

Не реализованы: у событий и задач нет правила повторения, каждая запись одиночная.

### (37) Что делает эндпоинт sync?

`GET /api/sync?since=...&device_id=...` отдаёт заметки, задачи и события, изменённые после указанного времени (включая удалённые, с флагом `isDeleted`), и запоминает время синхронизации устройства в `sync_checkpoints`. Синхронизация только в одну сторону (сервер → клиент), разрешения конфликтов нет; колонка `version` заложена в схему, но не используется.

### (38) Форматы экспорта и потоковая передача?

DOCX (`python-docx`) и PDF (`fpdf2`) для одной заметки. Файл собирается целиком в памяти (`BytesIO`) и отдаётся одним `Response`, потоковой передачи нет.

### (39) Пагинация и сортировка списков?

Пагинации в API нет, отдаётся весь список пользователя. Сортировка фиксированная: заметки по дате изменения (новые сверху), задачи по приоритету и сроку, события по началу.

### (40) Что будет при циклических ссылках между заметками?

Ничего страшного: A→B и B→A — это просто две строки в `note_links`, граф обходить не нужно. Запрещена только ссылка заметки на саму себя (`CHECK source <> target`); подзадач в проекте нет.

### (63) Какие автотесты есть?

Автотестов в репозитории нет, покрытие 0%. Это первый пункт в планах развития.

### (64) Как изолирована тестовая БД?

Не настраивалась, потому что тестов нет. Правильный вариант — отдельная БД или контейнер для тестов и откат транзакции после каждого теста.

### (65) Какие граничные случаи проверяют тесты для wiki и дат?

Тестов нет. Стоило бы проверить пустые wiki-ссылки без текста внутри, дубли, разный регистр, ссылку на себя и события, где конец раньше начала.

### (66) Какие линтеры и форматтеры использовались?

Конфигураций линтеров (ruff, black, eslint, prettier) в репозитории нет. Код проверялся запуском и подсказками редактора.

### (67) Как сделано логирование?

Только стандартный лог Uvicorn: каждый HTTP-запрос и необработанные ошибки пишутся в консоль контейнера (`docker compose logs api`). Журнала действий пользователей нет.

### (68) Ограничения монолита при масштабировании?

API можно запустить в нескольких копиях, потому что JWT без серверных сессий, но вложения лежат на локальном диске (том `uploads`), и все копии упрутся в одну PostgreSQL. Для роста нужны общее файловое хранилище (S3), пул соединений и пагинация.

### (69) Самый сложный участок?

Экспорт DOCX/PDF: из-за кириллицы в имени файла сервер падал при отправке заголовка `Content-Disposition`, а в PDF не было шрифта с кириллицей. Решили через `filename*=UTF-8''...` (RFC 5987) и подключение TTF-шрифта DejaVu/Arial.

### (70) Что внедрить в первую очередь для коммерческой эксплуатации?

Автотесты, уведомления в Telegram о дедлайнах, а также закрыть дыры безопасности: rate limit на вход и проверку заблокированных пользователей на каждом запросе. Плюс пагинация и healthcheck в docker-compose.

## FRONTEND

### (41) Почему Zustand, а не Redux или Context?

Глобально хранится только сессия (токены, имя, роль), и для этого Redux избыточен. Zustand — это одна функция `create`, встроенный persist для `localStorage` и меньше лишних перерисовок, чем у Context.

### (42) Как устроен authStore и где хранится токен?

`store/authStore.js` хранит `accessToken`, `refreshToken`, `userId`, `displayName`, `role` и методы `setSession` / `logout`. Через persist всё сохраняется в `localStorage` под ключом `ticktick-auth`, а после перезагрузки страницы восстанавливается оттуда.

### (43) Главная уязвимость JWT в localStorage?

Если на страницу попадёт вредоносный скрипт (XSS), он прочитает `localStorage` и украдёт токены. Снизить риск помогают короткий access-токен (у нас 15 минут), Content-Security-Policy и хранение refresh-токена в httpOnly-cookie.

### (44) Как работают interceptors в client.js?

Перехватчик запроса добавляет заголовок `Authorization: Bearer <токен>` из authStore. Перехватчик ответа при 401 один раз вызывает `/api/auth/refresh`, повторяет исходный запрос с новым токеном, а если refresh не удался — делает logout.

### (45) Что будет, если несколько запросов одновременно получат 401?

Каждый запустит свой refresh; первый получит новые токены и тут же отзовёт старый refresh, а остальные получат отказ и вызовут logout. Пользователя может неожиданно выкинуть на вход; исправляется общей очередью, где все ждут один refresh.

### (46) Как сделаны индикаторы загрузки и ошибки?

На каждой странице свой флаг `loading` и компонент `Loader` (спиннер Ant Design), ошибки показывает компонент `ErrorMessage` с текстом из `client.js`. Успешное сохранение заметки показывает `message.success("Сохранено")`; единого глобального индикатора нет.

### (47) Как защищены приватные маршруты и что будет при вводе `/admin`?

`ProtectedRoute` без токена перенаправляет на `/auth/login`, а `AdminRoute` при роли не admin перенаправляет на главную; пункт «Админ-панель» в меню видят только админы. Даже если обойти фронт, бэкенд на `/api/admin/*` вернёт 403.

### (48) Защита от race condition при быстрой смене заметок?

На странице заметки отдельной защиты нет: если старый ответ придёт позже нового, он может перезаписать данные на экране. В поиске есть задержка 300 мс с отменой таймера, но не отмена самого запроса; правильное решение — `AbortController`.

### (49) Как санитизируется Markdown от XSS?

Markdown не превращается в HTML: текст показывается в обычном `TextArea`, а React экранирует любой текст. `dangerouslySetInnerHTML` в проекте не используется, поэтому внедрить скрипт через заметку нельзя.

### (50) Как разбит интерфейс на компоненты и как избегали лишних перерисовок?

Есть 9 страниц (`pages/`) и 20 небольших компонентов (`components/`): карточки, формы, списки, layout, защита маршрутов. Компоненты подписываются на одно поле стора (`useAuthStore((s) => s.role)`) и перерисовываются только при его изменении; для списка тегов используется `useMemo`.

### (51) Как работает переход по wiki-ссылкам в интерфейсе?

Кликабельных ссылок в редакторе нет, двойные скобки в тексте остаются обычным текстом. Связи считаются на сервере и приходят в ответе API (`outgoingLinks` / `incomingLinks`), но в интерфейсе пока не выводятся.

### (52) Как статус задачи из календаря попадает в список задач?

Никак: календарь показывает события (`calendar_events`), а не задачи, это разные сущности. На странице задач после отметки галочкой список просто заново загружается с сервера.

### (53) Как настроен календарь Ant Design (локаль, часовые пояса)?

Всё приложение обёрнуто в `ConfigProvider` с русской локалью `ruRU`. Даты события выбираются через `RangePicker` (dayjs) в местном времени, а на сервер уходят в UTC через `toISOString()`.

### (54) Как валидируются формы на клиенте?

Формы входа и регистрации используют правила Ant Design Form: email обязателен и проверяется формат, пароль обязателен, при регистрации — минимум 6 символов. В задачах и событиях кнопка не отправляет запрос, если пустое название или не выбраны даты.

### (55) Какие оптимизации бандла применены?

Стандартная production-сборка Vite (минификация, tree-shaking). Ленивой загрузки маршрутов (`React.lazy`) и разделения на чанки нет.

### (56) Как устроен multi-stage Dockerfile фронта?

Первый этап `node:20-alpine` ставит зависимости и выполняет `npm run build`. Второй этап `nginx:alpine` копирует только папку `dist` и раздаёт её, поэтому Node.js в итоговом образе нет.

### (57) Как решена проблема F5 на `/calendar` в Docker?

В `nginx.conf` стоит `try_files $uri $uri/ /index.html`: если файла с таким путём нет, nginx отдаёт `index.html`. Дальше React Router сам показывает нужную страницу.

### (58) Почему браузер ходит на `localhost:8000`, а не на имя сервиса из compose?

Код фронтенда выполняется в браузере на компьютере пользователя, а имена сервисов вроде `api` существуют только внутри Docker-сети. Поэтому при сборке зашивается `VITE_API_URL=http://localhost:8000` — порт API, проброшенный на хост.

## База данных и инфраструктура БД

### (11) Какие нормальные формы соблюдены и где денормализация?

Схема в целом в 3НФ: пользователи, заметки, задачи, события, ссылки и вложения разнесены по таблицам и связаны внешними ключами. Сознательная денормализация: теги — массив `TEXT[]` прямо в `notes`, а `search_vector` для поиска заполняется триггером из заголовка и текста.

### (12) Зачем и `ticktick_schema.sql`, и Alembic, что главное?

`ticktick_schema.sql` создаёт полную схему при первом запуске контейнера PostgreSQL: таблицы, индексы, триггеры, функцию поиска. Alembic донакатывает изменения на уже существующую базу (миграция добавляет колонку `role`); источник истины для новой установки — SQL-скрипт.

### (13) Какие связи между таблицами?

Один-ко-многим: пользователь → заметки, задачи, события, refresh-токены; заметка → вложения. Многие-ко-многим: заметки между собой через `note_links`; задача и событие могут необязательно ссылаться на одну заметку (`linked_note_id`).

### (14) Как настроены CASCADE и SET NULL?

При удалении пользователя каскадом удаляются его заметки, задачи, события, токены и checkpoint-ы; при удалении заметки — её ссылки и вложения (`ON DELETE CASCADE`). У задач и событий поле `linked_note_id` при удалении заметки становится NULL (`ON DELETE SET NULL`); «проектов» в схеме нет.

### (15) Какие индексы есть и как проверить их использование?

Заметки: частичный индекс по `user_id` (не удалённые), `(user_id, updated_at DESC)`, GIN по `tags` и по `search_vector`. Задачи: по `user_id` и частичный `(user_id, due_at)` для невыполненных; проверка — `EXPLAIN ANALYZE` запроса в pgAdmin, в рамках проекта формально не замерялось.

### (16) В каком формате и часовом поясе хранятся дедлайны?

Тип `TIMESTAMPTZ`: PostgreSQL хранит момент времени в UTC и переводит в часовой пояс клиента при чтении. API сравнивает сроки с `datetime.now(timezone.utc)`, поэтому пользователи из разных регионов видят корректное время.

### (17) Как связаны задачи и календарь?

Напрямую не связаны: `todos` и `calendar_events` — две независимые таблицы. Общее у них только необязательная ссылка на заметку `linked_note_id`.

### (18) Какие ограничения целостности есть в самой СУБД?

UNIQUE на `users.email`, `refresh_tokens.token_hash`, пару `(source, target)` в ссылках и `(user_id, device_id)` в sync. CHECK: приоритет задачи 1–3, у события конец не раньше начала, заметка не ссылается сама на себя; плюс NOT NULL на ключевых полях и внешние ключи.

### (19) Что будет при миллионах записей?

Первыми упрутся списки без пагинации (`GET /api/notes`, `/api/todos` отдают всё сразу) и полнотекстовый поиск с `ts_headline` по большим текстам. Индексы по `user_id` помогают, но нужны пагинация, а для очень больших объёмов — архивирование или партиционирование.

### (20) Какой уровень изоляции транзакций и защита от гонок?

Используется уровень PostgreSQL по умолчанию — READ COMMITTED, явно не меняется. При одновременном редактировании одной заметки побеждает последнее сохранение; колонка `version` для оптимистичной блокировки есть, но API её не проверяет.

### (59) Почему порт 5434, а не 5432?

5434 — порт на компьютере разработчика, чтобы не конфликтовать с локально установленным PostgreSQL на 5432 (`ports: "5434:5432"`). Внутри Docker-сети API подключается к `db:5432`, это задано в `DATABASE_URL` в docker-compose.

### (60) Как гарантируется, что API не стартует раньше готовности БД?

`depends_on` задаёт только порядок запуска контейнеров, но не ждёт готовности PostgreSQL, healthcheck не настроен. Ожидание есть в `init_db.ps1`: он до минуты проверяет `pg_isready`; в compose правильнее добавить healthcheck и `condition: service_healthy`.

### (61) Как сохраняются данные между перезапусками?

Именованный том `pgdata` хранит файлы PostgreSQL, а том `uploads` — вложения. `docker compose down` и пересборка данные не трогают, удаляет их только `down -v`.

### (62) Зачем `init_db.ps1` и как развернуть на Linux?

Скрипт для Windows одной командой пересоздаёт БД: удаляет том, поднимает db и api, ждёт готовности и показывает список таблиц. На Linux достаточно установить Docker и выполнить `docker compose up -d --build`: схема накатится из SQL, миграции — командой `alembic upgrade head` при старте API.
